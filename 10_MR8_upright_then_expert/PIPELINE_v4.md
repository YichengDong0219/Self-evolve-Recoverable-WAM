# MR8 v4 失败恢复数据采集 pipeline（当前推荐版本，2026-11-01 冻结）

**一句话：** FACT 挂杯失败、杯子掉在桌上之后，用 cuRobo 把杯子就近扶正，立在专家工作过的区域里，再交给 RoboTwin 官方专家流程把杯子挂上。每个失败状态从逐位重放的现场反复试候选，只保留通过全部质量门控的那一条。

- v4 的代码对应本分支的提交 `1f95014`。目前目录里的代码等同于 v4（`CLOSED_TRANSIT = False`）。
- 冒烟测试：在 40 个分层抽样的状态上，合格 7/36（19%），约 0.4 GPU 小时一条；7 条全部 ≤ 900 步，状态 z ≤ 5.37。

## 1. 输入
- **失败状态资产 `rf_hanging_mug_v1`：** 845 个 base FACT 的失败状态，其中 757 个是挂杯失败（右手松手后杯子掉落），这是本 pipeline 的处理对象；交接失败不纳入。
- **接管步：** 48 步动作块的边界上，杯子已经回落到桌面高度的那一刻（`mug_takeover_step.py`）。
- **前提：** 动作重放逐位一致，所以同一个失败现场可以反复重现，用来试不同的候选。

## 2. 单次接管尝试的流程（`mug_recovery_upright.py`）
1. **静置：** 等杯子在 10 帧内位移 < 1 mm、转角 < 0.5°，每 15 个仿真步录一帧，最长 3000 步。等待的帧会进入数据，但不算动作损失。
2. **松手、让开：** 还夹着杯子的手张开、抬起 8 cm；另一只手离杯子 < 12 cm 时抬起 10 cm。全程不回零。只有确实有手移动过，才再等一次静置。
3. **分类，三选一：**
   - **直接交专家：** 杯子直立、离架子 ≥ 12 cm，且已经在专家区域内。
   - **勾口拖拽：** 杯子直立，但在区域外（大多停在桌子后部）。手指合拢、前倾 45°/60°，伸进杯口往回拖。杯口几何来自 `mug_rim_geometry.json`。拖倒了就在同一次尝试里改走扶正流程。
   - **扶正：** 杯子侧躺。
4. **扶正候选，整链用 cuRobo 预先规划：**
   - **抓取：** RoboTwin 的 6 个杯沿抓取点 × 接近角（绕手指张合轴转 0°、±30°；直立的杯子另加 ±45°）× 是否绕接近轴翻转 180°。左右手都试，近的先试。
   - **整链：** 从当前关节状态出发逐段规划：预抓（8 cm，避开架子和杯子）→ 直线接近 → 抬起（10 / 7 / 5 cm 依次试）→ 预放置 → 放置。
   - **关节盒：** 先用 MR7 盒（专家 ∪ 失败前缀，每个关节 ±0.4 rad），没有可行方案时再用 z 盒（FACT 状态归一化下每个关节均值 ± 5.5σ）。
5. **放置点与朝向：**
   - **两块区域：** A 区是专家初始放杯区（x −0.25…−0.10，y −0.05…0.05），之后走 `play_once`；B 区是右手接杯区（x −0.04…0.14，y −0.16…0.04），之后走 S3-S4。
   - **选点：** 4 cm 网格，离架子底座 ≥ 18 cm，按离杯子当前位置由近到远排序。A 区额外加 8 cm 惩罚，因为 `play_once` 的路径约长一倍。
   - **朝向：** 杯柄朝向限定在专家场景的范围内（朝远离机器人的半平面），按需要的手腕转动从小到大试 7 个角度。目标位姿由"杯子立在该点、杯柄朝该方向"和"握持时手与杯子的相对位姿"直接算出。
6. **执行：**
   - 移到预抓位姿；姿态差 > 0.05 rad 时修正一次；直线接近后合爪、抬起。
   - 按手中杯子的实际位姿，从当前关节状态重新挑一个能规划通的放置点和朝向。
   - 放下、松手、撤离。撤离依次尝试：沿手臂后撤 8 cm → 竖直上抬 → 沿接近方向反退。只要杯子已立好，撤离失败不算扶正失败。
   - 再等一次静置，确认杯子直立（≤ 15°）、没有被夹着。
7. **官方专家完成剩余动作，挂杯区域不再加架子障碍物：**
   - **B 区：** S3-S4，即右手抓起 → 抬起 → 挂上，左手同时回原位，和 `play_once` 一致。
   - **A 区：** 完整 `play_once`，即左手抓 → 中间点 → 右手接 → 挂上。
8. **稳定性检查：** 释放后保持 100 个仿真步，再检查一次成功。

## 3. 选择（`sim_select_mr8.py`）
- **列方案：** 每个状态先列出可行候选（MR7 盒的在前，z 盒的在后）。
- **执行：** 最多执行 6 个候选，每个都从重放的现场重新开始，全程录像并保存完整数据。
- **选中：** 第一个通过全部门控、且有完整数据的候选。
- **早停：** 连续 3 次抓取失败就停止该状态。进程崩溃不写结论。
- **并行：** 集群 4 张 4090、每卡 3 个进程，跑 36 个状态约 42 分钟。

## 4. 门控（全部必须通过，G8 除外）
| 门控 | 要求 |
|---|---|
| G1 | 挂杯成功，且释放 100 步后仍成功 |
| G2 | 官方专家开始之前不回零 |
| G3 | 扶正最多抓一次 |
| G4 | 交给专家时杯子直立（≤ 15°） |
| G5 | 合爪前杯子位移 < 5 mm，从最后一次有意推杯之后开始算（同 MR6） |
| G6 | 挂杯之前没有掉落、掉出桌面、飞出等异常；有意推杯途中杯子被推动不算 |
| G7 | 单帧关节步长 ≤ 0.2 rad |
| Z | 恢复段每帧手臂状态在部署的 FACT 模型归一化下 \|z\| ≤ 5.63（第一轮审计规则：专家最大 5.13 + 0.5） |
| L900 | 失败前缀 + 恢复 ≤ 900 步（评测时限） |
| G8 | 旧规则（专家 ∪ 前缀 ±0.5 rad），只记录不要求：扶正需要专家没用过、但统计上正常的手腕角度 |

## 5. 输出与训练构造
- **数据：** 每条合格数据保存一个无损 npz（三路相机、状态、动作、杯子位姿），同一 seed 的专家演示另外采集。
- **训练构造沿用第一轮的设计：**
  - 失败前缀作为 FACT 失败 episode，只训练世界模型，不算动作损失；
  - 恢复段在 cuRobo 第一次动作之前的静置帧不算动作损失；
  - 之后的扶正段和专家段都算动作损失；
  - 价值通道关闭。

## 6. v4 实测（40 个分层抽样状态，36 个有效）
| 组 | 含义 | 合格 |
|---|---|---|
| K1 | 侧躺、完全找不到抓取位姿（多在桌子后部且杯口朝外） | 0/10（没有候选，几乎不耗算力） |
| K2 | 侧躺、能抓到但整链挂不上 | 2/9 |
| K3 | 侧躺、MR6 有可行方案 | 4/8 |
| K4 | 直立在桌子后部 | 1/9 |

- **数据质量：** 7 条都走官方 S3-S4；恢复段中位数 446 帧；放置点 5 个；杯柄朝向 30°、60°、90°、150°；5/7 条同时满足旧 G8。
- **对比：**
  - MR7 整体入选约 5%（C 档 0.3%），约 1–8 GPU 小时一条；
  - MR6 约 1.1 GPU 小时一条，但有关节绕圈问题；
  - v4 约 19%，约 0.4 GPU 小时一条。

## 7. 已知局限与待定事项
- **K1（约占挂杯失败的 31%）、多数 K4 还没解决：** 根本原因是竖直向下的夹爪只能够到 y ≤ 0.05，而掉落的杯子多停在 y 0.15–0.22。
- **抓取失败仍是主要损耗**（v4 共 63 次尝试，其中 34 次）：途中撞到杯子 11 次、起始关节超出 MR7 盒 8 次、直线接近被拒 5 次等。v5、v6 的修补都没有超过 v4。
- **挂上了但超 900 步（8 次）：** 主要是一开始要等掉落后的杯子滚动停下，最长 164 帧。
- **待你决定的数据风格问题：**
  - 勾口拖倒再扶正的轨迹，能否进训练数据？
  - 挂上后没能后撤的收尾瑕疵（例如 140127）要不要剔除？
- **评估噪声：** 每轮 36 个状态，±2 条以内的差别分不出是改动还是随机波动。

## 8. 运行方法

```bash
# cluster: ~/fact_local (code/ = MR7 mainline, code_mr8/ = this branch, first on PYTHONPATH via env_mr8.sh)
B=$HOME/fact_local/bench_mr8
python code_mr8/sim_select_mr8.py <jobs.jsonl> $B/<RUN> 0,0,0,1,1,1,2,2,2,3,3,3 6 \
  pp+seeds+rack+jbox+ns+boxchk,pp+seeds+rack+jboxz+ns+boxchk

```
任务列表的每一行：`{"rollout", "step", "group", "cat", "state_id"}`。资产里的状态可以用 `code/rf_assets.py` 生成任务列表。
